A variante agora carrega a causa e a mensagem a imprime. **A ocorrência que se esperava chegou — 18/09/2026**, no gate local, num terceiro teste: `receiver_restores_remote_moves_and_deletions_only_at_the_applied_path` (`recovery.rs:1224`), e a causa que 1.6.10 mandou carregar diz `ApplicationBlocked { cause: "timed out waiting for the workspace write lock" }`. **Isso nomeia o lock**, ao contrário dos dois primeiros, cujo `ApplicationBlocked` vinha de `notes_core::sync::capture` recusando num hash relido. São **cinco** testes com `timed out waiting for the workspace write lock` contra dois com o guard do `capture` — a variante do lock é a dominante, não a exceção, e aparece com a máquina ocupada (builds e gates simultâneos). **Próximo passo:** separar os dois caminhos pela string de causa, medir quanto tempo o write lock fica segurado durante `stage_receiver_edits`, e decidir se o timeout é curto demais para uma máquina carregada ou se há de fato quem o segure sem soltar. **22/09 — a contagem acima não é evidência do que parecia.** Em `1.7.10` a frase *"timed out waiting for the workspace write lock"* descobriu-se emitida de **quatro** lugares, e só um deles é esse lock: dois vêm do `try_lock` do arquivo de atividade (que não espera nada) e um de `sync.rs` quando a reconciliação não assenta em 201 passes, que não é lock nenhum.
