A variante agora carrega a causa e a mensagem a imprime. **A ocorrência que se esperava chegou — 18/09/2026**, no gate local, num terceiro teste: `receiver_restores_remote_moves_and_deletions_only_at_the_applied_path` (`recovery.rs:1224`), e a causa que 1.6.10 mandou carregar diz `ApplicationBlocked { cause: "timed out waiting for the workspace write lock" }`. **Isso nomeia o lock**, ao contrário dos dois primeiros, cujo `ApplicationBlocked` vinha de `notes_core::sync::capture` recusando num hash relido. Passou 3× isolado e o gate seguinte deu `all green`; a rodada vermelha **não** tinha outra sessão compilando, ao contrário das anteriores. **18/09 mais tarde — o mesmo `cause` em mais dois testes**, `ordinary_receiver_capture_preserves_remote_races_for_explicit_resolution` (`recovery.rs:2056`) e `receiver_recapture_reserves_resolution_capacity_without_discarding_history`, numa rodada sem nenhum Rust tocado. **19/09 — um quinto:** `a_second_receiver_move_before_confirmation_preserves_the_whole_history` (`recovery.rs:2323`), mesma causa, outra vez sem Rust tocado. São **cinco** testes com `timed out waiting for the workspace write lock` contra dois com o guard do `capture` — a variante do lock é a dominante, não a exceção, e aparece com a máquina ocupada (builds e gates simultâneos). **Próximo passo:** separar os dois caminhos pela string de causa, medir quanto tempo o write lock fica segurado durante `stage_receiver_edits`, e decidir se o timeout é curto demais para uma máquina carregada ou se há de fato quem o segure sem soltar. **22/09 — a contagem acima não é evidência do que parecia.** Em `1.7.10` a frase *"timed out waiting for the workspace write lock"* descobriu-se emitida de **quatro** lugares, e só um deles é esse lock: dois vêm do `try_lock` do arquivo de atividade (que não espera nada) e um de `sync.rs` quando a reconciliação não assenta em 201 passes, que não é lock nenhum. Os cinco casos foram contados pela string, então não se sabe quantos eram o write lock. Agora `LockTimeout { what: LockWait }` e `NotSettled { passes, queued }` separam as causas, e **a próxima ocorrência já chega discriminada** — medir o tempo de retenção do write lock só faz sentido se ela disser `WorkspaceWrite`. Separado disso, `1.7.15` achou um caminho que alimentava `NotSettled`: correlação que esgotava o orçamento de hash apagava o registro em vez de enfileirar, e o dreno de `inventory_using` esperava uma fila que nunca era escrita. **23/09 — a primeira ocorrencia discriminada, e nao e o write lock.** CI de `1.8.5` no macOS (run 35918936437, verde no rerun): `edits_during_transfer_are_recaptured_without_applying_the_older_publication`, `recovery.rs:2044`, `stage_receiver_edits` -> `timed out waiting for the activity state file (shared)` — o `try_lock_shared` do lease de atividade, que nao espera nada. Nenhum portador plausivel: o data dir e da fixture, nenhuma thread captura o lease e nada no binario faz fork. Entao a hipotese restante e erro de SO relatado como espera; desde `1.8.12` so `WouldBlock` vira `LockTimeout`, `EINTR` e tentado de novo e qualquer outro erro sai como I/O com o `kind` — **a proxima ocorrencia diz qual dos dois foi**. **23/09, mais tarde — disse:** CI de `1.8.15` no macOS, `saved_receiver_edits_publish_without_a_remote_conflict_or_source_rewrite`, `activity state file (exclusive)`, que depois de 1.8.12 so pode ser `WouldBlock`: ha um detentor real, no processo e no data dir da propria fixture, e a leitura nao o acha. Desde `1.8.43` a recusa imprime, em build de debug, a pilha de cada lease vivo daquele arquivo no processo — **a proxima ocorrencia nomeia o detentor** **24/09 — found, and it was outside the process.** The instrument fired twice on the macOS CI of `1.8.60`, a commit with no Rust in it (run 36040110533: `recovery.rs:1341` and `recovery.rs:2090`, both `activity state file (shared)`, both reporting 0 leases held in the process). The holder was a **process being spawned by another test's thread**: a spawned child carries a copy of every open descriptor until it execs, a `flock` belongs to the open file rather than the descriptor, so a lease dropped during that window stays locked by a process about to become something else. On macOS every note deletion spawns one — the `trash` crate asks the Finder through `osascript` — which is why this was macOS only. Measured on Linux with a thread spawning `/bin/true`: 274,000 refusals of an unheld lock in 1.4 million rounds, none in 1.3 million without it. **Fixed in `1.8.62`:** a refused activity lease is tried again for 250 ms before it is reported (the write lock already waits 5 s), and a test with a spawning thread fails in its first three rounds without that window. **Still open on this row:** the pre-`1.7.10` Linux occurrences, counted by a string four places emitted, have not recurred since the causes were told apart; this row leaves when the macOS CI has run a week without one | Implementation |
